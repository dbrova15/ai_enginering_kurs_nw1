## Перевірка еталону

Для кожного case перевірити питання, reference, релевантні чанки та символьні evidence spans у поточному `blocks.json`. Відкрити source URL/PDF-сторінку з manifest; окремо перевірити no-answer, схожі пристрої й версії. Лише після цього людина змінює `review_status` кейсу та envelope на `approved`. Не редагувати еталон заради кращого результату моделі.

Зручний перелік — [REVIEW.md](REVIEW.md). Relevant чернетки містить усі
regex-кандидати; буквальний збіг сам по собі не доводить достатність доказу.
Питання з версіями стосуються саме наданого PDF, а не порівняння двох
історичних редакцій. Якщо після review змінюються питання/reference/relevant,
попередній run залишається історичним; нові метрики не слід приписувати йому.

15 retrieval-кейсів є підмножиною 20 питань. Recall@5 — macro частка знайдених relevant IDs; MRR@5 — обернений ранг першого релевантного чанка. Числові метрики чернетки є provisional.

## Калібрування

Після нового окремо погодженого answer-run для затвердженого актуального testset вибрати ≥10 різних відповідей, включно з правильними й неправильними фактами/цитатами. Людина заповнює `correct`, `faithful`, пояснення та `approved`. SHA-256 відповіді й контексту мають відповідати run; шаблон із null-оцінками не є розміткою.

[ANSWER_REVIEW.md](ANSWER_REVIEW.md) містить усі 20 історичних extract-4 відповідей
із rendered source links. [labels.template.json](labels.template.json)
містить їхні hashes і порожні значення. Спочатку незалежно оцінити докази,
потім перенести перевірені записи в `labels.json` із boolean-оцінками,
поясненнями та `review_status=approved`. Не копіювати verdicts судді як
людські labels. Template із `correct=null` навмисно не проходить HumanLabel.
Для обох метрик потрібні ≥10 оцінених відповідей і обидва класи; якщо
реальних негативних випадків бракує, не вигадувати їх.

```powershell
.\.venv\Scripts\python.exe main.py rag calibrate --config .rag/paid-run.json --run-id <run-id>
```

Калібрування не можна виконати без заповнених labels. Correctness judge порівнює відповідь із reference, faithfulness — кожний атомарний факт із саме його cited sources. Agreement, false-pass і false-fail рахуються від усіх ручних прикладів. Зміна judge/model/prompt вимагає нового калібрування.

## CI

Платний автоматичний CI не активовано: automatic approval review відхилив його через передавання корпусу зовнішньому API й повторні витрати. Це не замінюється прихованими запитами зі скриптів. Офлайн-workflow перевіряє код; він не доводить виконання повного R16 із реальними відповідями моделей на кожний push/PR.

Майбутнє ввімкнення повних evals потребує конкретного дозволу на зовнішнє передавання, секретів, per-run бюджету й контролю загальних витрат, а також approved testset і калібрування. `pull_request_target` для коду fork PR використовувати не можна. Агент не робить commit/push і не заявляє справжній GitHub Actions-run лише за локальними тестами.

## Ліміти даних

Оригінали погоджено для локальної навчальної обробки. Право публічного поширення повних HTML/PDF та extracted chunks не підтверджено. До публікації перевірити цей аспект; downloader фіксує URLs і SHA-256, але змінений сайт може не віддати ті самі байти. Непридатні PDF glyphs/діаграми зазначені в manifest warnings, не інтерпретовані як факти.
