## Корпус і chunking

Погоджено для локальної навчальної обробки **36 унікальних документів**:
31 HTML зі свого технічного корпусу та 5 офіційних PDF Espressif/ST.
Мовний склад: 28 uk / 3 ru / 5 en. Дев'ять недоступних Arduino Blog URLs
виключено до приймання списку. Вихідні TXT ДЗ1 не конвертувалися штучно
для виконання вимоги двох форматів.

Поточний результат: **14 681 нормалізований блок, 2016 чанків**. Усі символьні
spans перевірені на існування й допустимі межі. HTML зберігає заголовки,
списки, таблиці й код; PDF зберігає сторінки, табличні рядки та геометрично
підтверджені merged cells. Невизначені PDF-розділи явно позначені сторінкою.
Зміст нормалізується до NFC/LF; exact duplicates зберігають source aliases.
Metadata містять URL, назву, розділ/сторінку, raw/content hashes і версію
або явний unknown. Новий dataset публікується атомарно лише після перевірок.

Початковий target — 320 токенів повного passage, hard cap — 384,
query cap — 96. Обидва локальні tokenizer перевіряються без hidden truncation;
це залишає місце для query/pair metadata в reranker із межею 512.
Heading-стратегія зберігає межі змісту, а довгі таблиці повторюють справжній
header із посиланням на його span. Fixed baseline має overlap=48.

Реальне [порівняння двох HTML та одного PDF](chunking-comparison-extract6.json):

| Джерело | Стратегія | Чанків | Median tokens | Max tokens |
| --- | --- | --- | --- | --- |
| HR-0001 | heading | 25 | 299 | 320 |
| HR-0001 | fixed | 23 | 319 | 320 |
| HR-0038 | heading | 9 | 313 | 319 |
| HR-0038 | fixed | 10 | 318.5 | 320 |
| DS-ESP32 | heading | 303 | 282 | 320 |
| DS-ESP32 | fixed | 241 | 320 | 320 |

Heading дає більше коротких структурних блоків у PDF. Ця статистика
не доводить переваги якості: відповідей двох chunking-стратегій не порівнювали.
[Sample structural QA](structural-qa.json) перевірив таблицю HR-0001,
усі 114 рядків скетчу HR-0038 і таблицю ESP32 page 52. Це перевірка агента,
а не людське затвердження golden. Повний візуальний QA всіх PDF не завершений.

## Пошук: поточний extract-6, 15 однакових draft-питань

Embeddings: локальний `intfloat/multilingual-e5-small`, 384D, один E5 prefix,
mean pooling і normalization. Лексичний пошук — BM25 із технічними tokens;
hybrid об'єднує ранги через RRF. Локальний `BAAI/bge-reranker-v2-m3-int8`
переранжовує top-20 до top-5. Мова/формат фільтруються однаково в усіх режимах.

| Конфігурація | Macro recall@5 | MRR@5 | N |
| --- | --- | --- | --- |
| Vector | 0.7337 | 0.7778 | 15 |
| Hybrid | 0.6393 | 0.7167 | 15 |
| Hybrid + reranking | **0.7389** | **0.9333** | 15 |

Recall — частка знайдених relevant chunk IDs для кейсу з подальшим
macro-середнім; MRR — обернений ранг першого relevant ID, максимум до rank 5.
Збережено rankings і розподіл за мовами. Значення цього локального extract-6
run збігаються з історичним extract-4 run; це два окремі artifacts, не
переписана baseline і не доказ приросту якості. Чистий hybrid тут гірший за vector;
це виміряний результат, а не підстава приховувати конфігурацію.

Поріг recall@5 = 0.8 **не пройдено**. Relevant у draft включає regex-кандидатів,
семантичну достатність яких ще має перевірити людина. Для HR-q08/q11 їх 14,
тому абсолютна межа recall@5 цих кейсів — 5/14. Не можна зменшувати gold
або поріг задля проходження: потрібна незалежна розмітка й узгоджене
трактування повторів доказів, після чого нові виміри мають новий lineage.

## Реальні відповіді extract-4 й попередні оцінки

Run `20261117T162104Z-71601edd`: **20 питань**, 18 answerable і 2 no-answer;
16 uk / 2 ru / 2 en. Є по два similar-model та outdated-query сценарії.
Останні перевіряють версію саме наданого PDF; це не історичне порівняння
двох редакцій документа. Питання й reference залишаються draft.

Generator і judge: requested `gpt-4o-mini`, actual `gpt-4o-mini-2024-07-18`.
Параметри й prompt hashes містяться в run; еталон не передавався generator.
Correctness judge бачив reference, faithfulness judge — лише відповідь
і фактичні джерела для її claims. Це одна сім'я моделей, тому можливі спільні
систематичні помилки; такий judge не є незалежним людським підтвердженням.

| Показник | Вимір | Межа інтерпретації |
| --- | --- | --- |
| Первинна структурна валідність | 20/20 | Формат та citation IDs, не істинність |
| Фінальна структурна валідність | 20/20 | Repair = 0, transport retries = 0 |
| Технічні failed | 0/20 | Не вилучалися б зі знаменників |
| Correctness | 18/18 | Некалібрований judge, draft reference |
| Релевантне джерело | 18/18 | Перетин із draft relevant IDs |
| Faithfulness | 18/18 | Некалібрований judge; див. зауваження нижче |
| Правильна відмова | 2/2 | Лише два явно вигадані no-answer кейси |
| False abstain | 0/18 | Answerable частина цього прогону |
| Формальні цитати | 73/73 | IDs належать переданому контексту |
| Judge agreement / false pass / false fail | Не виміряно | Немає людських labels |

100% автоматичних позитивних verdicts **не означають 100% фактичної якості**.
Відсутні human review і calibration самі по собі блокують фінальне приймання.

Latency, nearest-rank, секунди:

| Етап | N | p50 | p95 |
| --- | --- | --- | --- |
| Retrieval | 20 | 5.075 | 5.825 |
| Retrieval + generation | 20 | 9.351 | 15.290 |
| Увесь кейс із judge | 20 | 16.045 | 25.851 |

Таймери generation pipeline включають retry/repair за їх наявності;
у цьому запуску їх не було. Моделі вже були завантажені в процес для
retrieval comparison. Cold start окремо не виміряний; ці цифри не є
окремим cold benchmark і не гарантують latency іншого обладнання.

## П'ять зауважень за реальними артефактами

Нижче — аналіз агента для review, **не людські labels** і не переписані
автоматичні метрики. Не всі зауваження є хибним фактом: окремо позначено
ризик атрибуції, зайвий зміст, retrieval trade-off і втрату extraction.

1. **HR-q01: недостатня умова про живлення.** Питання стосується LCD-шилда
   зі статті HR-0056, reference вказує 3.3V. Модель додала можливість роботи
   «від 5V до 3.3V», пославшись на `ccd8581f…` зі схожої статті HR-0055.
   Сам chunk говорить про зміну підключення до ніжки стабілізатора,
   а не безумовний діапазон напруги довільного шилда. Judge прийняв це
   без застереження. Це кандидат на false pass/помилку атрибуції;
   потрібно зберігати умову модифікації та прив'язку до конкретної статті.
2. **HR-q13: зайва модель у відповіді.** На питання про ROM ESP32 надано
   правильні 448 KB, а також непрошені 384 KB ESP32-S3 з іншого PDF.
   Назви моделей не змішані, тому це не доведена числова помилка,
   але retrieval/context дозволили зайве порівняння. Потрібна перевірка
   релевантності кожного claim саме питанню, а не лише його доказовості.
3. **HR-0038: змінений string literal під час cleanup.** Скетч
   загорнутий у звичайні HTML `<p>`, тому стара нормалізація прози стискала
   чотири пробіли в `lcd.print("    TERMOBOX")`. Це реальний дефект ingestion,
   знайдений під час sample QA, а не вигадана помилка відповіді. Extract-6
   розпізнає всі 114 code-параграфів, зберігає tabs/literals/`<br>`; regression
   test перевіряє також inline spans і `else`-call. Платний run не повторено.
4. **HR-q02: reranking погіршує покриття.** Для однакових восьми draft
   relevant IDs vector і hybrid знаходять 5/8, а reranking — 2/8;
   перший relevant при цьому залишається rank 1. Отже, вищий MRR не означає
   кращого покриття доказів. Спершу людина має перевірити ці вісім relevant;
   наступний контрольований експеримент може змінювати candidates/k/fusion,
   але не еталон за результатами моделі.
5. **DS-STM32F103VD: неповне PDF extraction.** Audit містить 1479 подій
   на 60 різних сторінках цього PDF, зокрема нерозкодовані graphic glyphs
   і таблиці. Це не 1479 сторінок. Такі ділянки не перетворюються на
   вигаданий текст, але частина доказів недоступна для RAG. Візуально
   перевірений merged-cell випадок ESP32 page 52 виправлено геометрично;
   для решти потрібні окремий QA й погоджене рішення щодо OCR/іншого parser.

Ці зауваження збережено без нового prompt tuning або платного повтору.
Машинні оцінки в первинному run залишаються незмінними для аудиту.

лише retrieved snippets із погоджених публічних джерел, cap **$0.25**.

## Перевірки й межі приймання

- По 112 офлайн unit/integration tests пройдено на Windows/Python 3.11
  та Ubuntu 24.04 WSL/Python 3.12.
  Є справжні малі HTML/PDF ingestion і Qdrant tests, fake-provider ask E2E,
  перевірки budget/retry/repair, sources, scoring, judge та docstring/comments.
- Фінальний локальний [Linux model smoke](linux-smoke-extract6.json): batch 4,
  CPU arena disabled, 2×384 нормалізованих
  E5 vectors, BGE правильно ставить ROM chunk вище unrelated Sumo chunk;
  weights використані повторно, жодних model API calls/downloads.
- Для історичного тесту ДЗ1 шляхи fixture переносні в пам'яті;
  `generate_report.py` допускає лише absolute 1e-12 різницю float через
  зміну `sum` у Python 3.12, із точними hashes/структурою та negative test.
  Історичні звіти й метрики на диску не переписані.
- [Resource checks](resource-checks.json) фіксують реальні memory/incomplete
  failures та успішну фінальну індексацію. Peak-memory benchmark не
  вимірювався; batch/arena profile не змінює дозволені weights. Сторонні
  системні процеси агент не зупиняв. CLI native failures тепер дають exit 2
  без raw exception body.
- `pip check` на обох платформах без конфліктів; усі 74 protected hashes ДЗ1 незмінні;
  усі chunk spans мають коректні межі. `git diff --check` без whitespace errors.
- Provisional lint: 20 кейсів пройшли структурну перевірку.
  `full --gate` на неперевіреному testset повертає exit 2 до API.
- Report повторно отримано із saved run без моделі.
- [Офлайн-workflow](../../.github/workflows/hw2-offline.yml) перевіряє код
  на push/PR без corpus-to-API, secrets або оплати. YAML перевірено локально;
  справжнього GitHub Actions-run агент не виконував і commit/push не робив.

Повний R16 quality CI не активовано: автоматична approval-перевірка
відхилила передавання корпусу зовнішньому API та повторні витрати.
Дозвіл на один локальний run не дозволяє регулярний платний CI.
Права публічного поширення повних originals/chunks не підтверджені;
локальний корпус містить публічні авторські підписи, але окремий аудит
усіх персональних відомостей не проводився. Перед публікацією потрібна перевірка.

До приймання залишаються незалежне затвердження 20 cases, ≥10 реальних
людських correct/faithful labels обох класів, калібрування judge, проходження
узгодженого retrieval/answer gate та справжній quality CI. Якщо реальних
негативних прикладів після review бракуватиме, їх не можна вигадати або
підставити змінені відповіді як результати моделі: окремо погодити
наступний обмежений експеримент.

**Production-рішення:** готовність до production не підтверджена. Hybrid +
reranking залишається кандидатом цього зрізу завдяки кращому MRR і фактично
вищому macro recall, але провал recall-порогу та некалібрований judge
не дозволяють рекомендувати його як прийняту production-конфігурацію.
