# ДЗ3 · Agent System — дизайн

## Поточний стан і ціль

ДЗ2 відкриває корпус та індекс через `hardware_rag/runtime.py`, шукає через `Retriever.search` і перевіряє ідентифікатори цитат у `hardware_rag/generation/pipeline.py`. Поточний RAG-конвеєр вибирає пошук до генерації. ДЗ3 використовує ці наявні примітиви, а рішення про наступний крок належить моделі. Формати документів та індексу ДЗ2 не змінюються.

## Організація коду

| Область | Відповідальність | Вимоги |
| --- | --- | --- |
| `hardware_agent/cli.py`, підкоманда `main.py agent` | Запуск сесії, явний ввід користувача, конфігурація, життєвий цикл MCP | R05, R08, R09, R12 |
| `hardware_agent/loop.py`, `model.py`, `limits.py`, `trace.py` | Цикл, адаптер моделі, спільний облік лімітів, структуровані події | R01–R04, R07, R11 |
| `hardware_agent/tools/` | Схеми, диспетчеризація, політика доступу, пошук, підтверджений запис відгуку і симуляція збоїв | R01, R03, R04, R06, R07, R09 |
| `hardware_agent/mcp_server.py`, `mcp_client.py` | Локальні сервер і клієнт через stdio, перевірка меж протоколу | R05, R06 |
| `hardware_agent/session.py` і сховище відгуків | Короткострокова історія, ізоляція сесій, підтвердження й атомарний запис | R04, R08, R09 |
| `prompts/hw3/`, `evals/hw3/`, `tests/`, README | Версії промптів і описів, сценарії, trace, звіти й інструкції | R01, R10–R13 |

Код ДЗ3 розміщується в окремому пакеті. Зміна `main.py` обмежена делегуванням нової підкоманди. Для звіту ДЗ3 шлях `evals/hw3/REPORT.md` зберігає назву артефакту та чинний кореневий звіт ДЗ1. README посилається на звіт ДЗ3 та `REFLECTION.md` у корені.

## Інструменти й доступ — R01, R04–R07, R09

| Інструмент | Вхід та результат |
| --- | --- |
| `search_corpus` | Обмежений текст запиту й опційні enum-фільтри з ДЗ2. Повертає top-k дозволених уривків із `chunk_id`, `doc_id`, текстом і походженням. |
| `get_source_metadata` | Виклик через MCP. Приймає один `doc_id` у допустимому форматі. Повертає назву, URL і дату/версію, якщо вони відомі, або структуровану помилку. |
| `submit_feedback` | Ідентифікатор відповіді поточної сесії та рейтинг чи текст виправлення. Записує після окремого підтвердження й повертає ідентифікатор запису. |

MCP читає лише фіксований локальний каталог метаданих із перевіреної конфігурації запуску. Виклик не передає шляхи, URL для читання або довільні вирази. Сервер перевіряє дозволи самостійно. Retrieval отримує дозволену підмножину до пошуку й перевіряє результати перед видачею, щоб захищені уривки й метадані не були доступні через інший маршрут. Для цього адаптер ДЗ3 використовує чанки та індекс, сформовані з дозволеної підмножини, коли профіль обмежений. Deny-by-default стосується джерел поза каталогом доступу. Транспорт stdio локальний, CLI заповнює серверне оточення лише потрібними параметрами. Каталог можна читати окремим довіреним MCP-клієнтом, наприклад внутрішньою утилітою аудиту джерел.

Аргументи й результати перевіряються на межі кожного інструмента. Для MCP є серверна перевірка аргументів і клієнтська перевірка відповіді. Невалідні чи недозволені дані в контекст моделі не потрапляють. Евал на відмову робить реальний виклик MCP на обмежене джерело і перевіряє, що інший інструмент також не повертає захищених відомостей.

## Цикл, стан і збої — R01–R04, R07

Адаптер моделі повертає один виклик, уточнення або фінальну відповідь. Агент передає результат інструмента як окреме повідомлення; уривки мають ознаку недовірених даних. Стан запиту зберігає тільки фактично видані моделі докази й підстави зупинки. Факти про корпус проходять перевірку цитат за виданими `chunk_id`; за відсутності доказів є сценарій `not_found`. Для запиту без потреби в корпусі дозволено пряму відповідь без цитат. Для контрольного конфлікту eval звіряє обидва ID та вибрану версію за датою набрання чинності. За завершення бюджету CLI показує перевірені витяги з посиланнями або повідомлення про їх відсутність без додаткового виклику моделі.

На вході в цикл встановлюється монотонний дедлайн. Перед кожною спробою обліковуються крок і доступний час; перед викликом моделі резервуються токени або вартість із верхньою межею відповіді. Backoff обмежений рештою дедлайну, SDK retry вимикається або враховується тим самим обліком. Блокувальний локальний retrieval виконується в керованому воркері з контрольованим завершенням після таймауту. Невідомий usage позначається у trace, резерв не вивільняється як нуль. Fault-обгортка для тестових профілів підставляє задані таймаути, 429/503 та несумісні відповіді до перевірки результату. Повтори дозволені лише для читання й тимчасових помилок. Trace фіксує ID запуску, версії, кроки, спроби, тривалість, залишок бюджету, класи помилок, цитати, підтвердження та stop reason. Ключі й сирі тексти сесій у trace за замовчуванням відсутні.

## Пам’ять, підтвердження і дані — R04, R08, R09

Пам’ять активної CLI-сесії зберігає останні повні пари реплік у межах токенного ліміту. Найстаріші пари видаляються першими. Сесія видаляється після завершення процесу або явного скидання. Збережений відгук для поточної сесії завантажується під окремим типом даних. Наступна відповідь може врахувати уточнення користувача, а факти про корпус знову звіряються з джерелами.

До показу підтвердження обов’язкові поля валідуються й параметри нормалізуються. CLI показує дію та параметри, отримує згоду через окремий шлях вводу і передає одноразове підтвердження, прив’язане до сесії, дії та відбитка параметрів. Модель і документи не мають доступу до цього механізму. Для повторів одного підтвердженого наміру зберігається стабільний ключ межі операції. Пропоноване локальне SQLite-сховище ДЗ3 використовує унікальний ключ і транзакцію, щоб повтор після втрати відповіді повернув попередню квитанцію. Зміна параметрів вимагає нової згоди. Відгуки зберігаються локально до очищення користувачем; README документує спосіб видалення й відсутність перенесення активної історії між сесіями.

## Перевірка та ризики — R10–R13

Контрольні документи з інструкцією та двома версіями правила входять в окремий eval-профіль, де вони індексуються разом із замороженим зрізом корпусу ДЗ2. Оригінали, labels і результати ДЗ2 не редагуються. Офлайн-тести зі scripted model покривають цикл і збої, окремі інтеграційні тести запускають MCP stdio та перевіряють політику доступу. Фінальний набір запускається з реальною моделлю, а перевірки змісту використовують структуровані очікувані факти, ID джерел і trace. Для звіту порівнюються ті самі версії набору, корпусу, промптів і лімітів. Fixture-ін’єкції й контрольні збої позначаються; фактичні результати не домислюються.

Основні ризики — неточні оцінки токенів, блокування локального пошуку, недетермінований вибір інструмента й розбіжність метаданих між каталогом та індексом. Потрібні перевірки завершення воркера, узгодженості каталогу з корпусом, стабільності кількох реальних прогонів за потреби. До реалізації погоджуються архітектура, нова залежність MCP SDK і локальне сховище. Платні виклики потребують окремого погодження моделі, тарифів і бюджету.
