## Мета і межі

HardwareResearch AI використовує корпус і пошук ДЗ2. Агент сам керує викликами інструментів, відповідає з перевірними джерелами та враховує контекст і відгук. ## Критерії приймання

### Агент і виконання

- **R01. Рішення агента.** Коли надходить запит, модель з підтримкою tool calling вирішує, чи відповісти одразу, чи викликати інструмент із власними аргументами, чи уточнити або повторити пошук. Потрібні щонайменше два вузькі інструменти. Опис кожного задає призначення, умови виклику, аргументи та результат. Описи, схеми й системний промпт версіонуються окремо від реалізації.
- **R02. Ліміти.** Для кожного запиту діють ліміт кроків, бюджет токенів або грошей, таймаут окремого виклику й дедлайн усього запиту. Коли ліміт вичерпано, агент припиняє нові виклики, повертає вже підтверджений частковий результат або пояснює, чого бракує. Trace фіксує причину зупинки.
- **R03. Збої.** Якщо аргументи невалідні, інструмент породжує виняток або повертає несумісний результат, агент отримує безпечний опис помилки. Для таймауту, 429 і 503 дозволено обмежені повтори лише безпечних операцій із backoff у межах R02. Після вичерпання спроб агент повідомляє про недоступність. Зміна формату видима у trace. Fault injection відтворює обидва класи збоїв.
- **R04. Побічні ефекти.** Якщо інструмент виконує зовнішню щодо розмови дію, код вимагає підтвердження людини для конкретних параметрів. За браку обов’язкового параметра агент перепитує. Повтор або обрив після застосування підтвердженої дії не створює дубля. Непідтверджені дії блокуються й відображаються у trace.

### MCP і джерела

- **R05. Протокол.** Власний локальний MCP-сервер надає щонайменше один інструмент, який агент фактично викликає як MCP-клієнт у наборі задач. README пояснює цінність окремого MCP і називає потенційного іншого споживача.
- **R06. Межі доступу.** MCP-сервер перевіряє типи й обмеження аргументів, застосовує дозволи до конкретного джерела та пропонує лише вузькі операції. Довільні SQL, shell і файлові шляхи не приймаються. Після відмови агент пояснює обмеження й не дістає захищені дані іншим інструментом.
- **R07. Підтвердження джерелами.** Докази про корпус походять із реально отриманих уривків ДЗ2. Якщо перевірних доказів бракує, агент прямо про це повідомляє. Інструкція в уривку залишається даними й не спричиняє дій. За двох різних датованих версій одного правила агент обирає чинну на дату запиту, пояснює суперечність і цитує обидві.

### Пам’ять і відгук

- **R08. Пам’ять.** Наступний запит у тій самій сесії може використовувати попередній контекст. Документація визначає дані, межі обсягу, час зберігання та видалення. Сесії ізольовані.
- **R09. Відгук.** Користувач може оцінити чи виправити конкретну відповідь. Тест або діалог у README демонструє вплив відгуку на наступну відповідь. Виправлення автора діалогу не підміняє корпус як джерело тверджень.

### Оцінювання і здача

- **R10. Перевірки.** Щонайменше 15 задач із детермінованими перевірками змісту, дотримання лімітів, потрібних викликів та відсутності дій без дозволу. Набір охоплює запити без інструмента і без відповіді, реальний MCP-виклик, відмову в доступі та всі збої й граничні сценарії R02–R09.
- **R11. Звіт.** Збережено результати й trace фінального прогону, за нестабільності є повторні прогони. REPORT.md містить частку пройдених задач, потрібні виклики, непогоджені ефекти, кроки й вартість на задачу, для платної моделі — оцінку на 1000 запитів. Є розбір трьох фактичних провалів і таблиця збоїв із очікуванням, першим результатом і внесеною зміною.
- **R12. Відтворення.** Агент запускається однією командою після описаної підготовки. README пояснює запуск MCP, інструменти, пам’ять і відгук. Конфігурація ключів іде через локальний .env, у Git є тільки шаблон. Для здачі потрібне одне посилання на GitHub із доступом лектора.
- **R13. Рефлексія.** REFLECTION.md містить 3–5 фактичних епізодів роботи з coding-агентом, конкретні результати, потрібні правки й спосіб перевірки з посиланнями на файли або коміти. Робочі інструкції агента є в репозиторії.
