# HardwareResearch AI

Навчальний проєкт для **Homework 1: Structured Extraction Service**. Сервіс витягує структуровані відомості з технічних статей про електроніку, мікроконтролери, IoT та робототехніку й зберігає результати у JSONL.

Єдина схема нової генерації — **Schema v2**, строгий контракт **`schema-v2-enums-1`**, модель `DevicePosting` із `schema_contracts.py` (також доступна з `main.py`). Попередній `schema-v2-strings-1` збережений лише для офлайнового відтворення історії. [Правила контрактів і наступні етапи](docs/SCHEMA_V2_CONTRACTS.md). Реалізація — CLI на Python із Pydantic v2, JSON Schema та OpenAI-сумісним Chat Completions API. Підтримку конкретними endpoint нового контракту ще потрібно перевірити окремо дозволеними probes.

## Поточний стан

- Є 30 вихідних TXT: 18 українською, 9 англійською, 3 російською.
- У `data/sourses/hm1/golden.json` є 10 еталонних записів Schema v2 зі статусом `approved`.
- Реалізовано читання статей, підготовку тексту, запити до моделі, валідацію, одну repair-спробу та збереження відповідей.
- Є дві версії промпту й офлайн-тести.
- Є evaluator: accuracy восьми полів, aggregate accuracy, content accuracy семи полів без `language`, micro precision/recall/F1 списків та розбіжності з golden.
- У `results/` збережено 240 відповідей (8 прогонів) за **історичним list[str]-контрактом**, а не за новими enum. [Попередній REPORT.md](REPORT.md) і [нотатки експерименту](results/sampling_comparison_20261026.md) залишені незмінними як історичні результати.
- Строгий контракт перевірено офлайн, двома probes і окремо дозволеною [матрицею 240 нових генерацій](results/schema-v2-enums-1/EXPERIMENT_20261026T173328975361Z.md). Фінально валідні 220/240; OpenAI — 120/120 одразу, Ollama — 100/120 після можливого repair. API-вартість матриці оцінена як $0.044028 із дозволених $0.25.
- [Новий звіт строгого контракту](REPORT.md) містить метрики восьми конфігурацій і п'ять перевірених розбіжностей. Найвищі виміряні aggregate/content accuracy — OpenAI v2/T=0.7: 92.50% / 91.43%. Авторське production-рішення потребує затвердження; старий REPORT не замінений.

## Установлення

Команди нижче призначені для PowerShell. Виконуйте їх із кореня проєкту.

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Створіть `.env` із прикладу, якщо його ще немає:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Оберіть провайдера через `LLM_PROVIDER` у `.env` або оточенні процесу. Допустимі значення: `openrouter`, `openai`, `ollama`; типово `openrouter`:

```dotenv
LLM_PROVIDER=openai
```

`get_provider()` нормалізує пробіли/регістр і перевіряє значення до мережі. Невідоме значення — помилка. `load_dotenv()` не перезаписує вже задані змінні процесу; Python-код для перемикання редагувати не потрібно.

У `.env` налаштуйте ключ, модель та інші параметри обраного провайдера за прикладами нижче. Ключі зберігайте локально: `.env` виключено правилами `.gitignore`.

### OpenRouter

У `.env`:

```dotenv
LLM_PROVIDER=openrouter
OPENROUTER_API_KEY=ВАШ_API_КЛЮЧ
OPENROUTER_MODEL=openai/gpt-4o-mini
```

### OpenAI

У `.env`:

```dotenv
LLM_PROVIDER=openai
OPENAI_API_KEY=ВАШ_API_КЛЮЧ
OPENAI_MODEL=gpt-4o-mini
```

### Ollama

У `.env`:

```dotenv
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=llama3.2:3b
```

Для Ollama зовнішній API-ключ не потрібний. Код додає `/v1` до адреси сервера, якщо такого суфікса ще немає. Назви моделей у прикладах відповідають типовим значенням коду й не є результатом порівняння якості.

### Параметри запиту

```dotenv
REQUEST_TIMEOUT_SECONDS=60
MAX_RETRIES=2
TEMPERATURE=0
TOP_P=1
```

`MAX_TOKENS` необов'язковий і не є вимогою ДЗ. Якщо змінна відсутня або порожня, `max_tokens` не передається в API-запит; діють обмеження моделі та провайдера. Щоб явно обмежити відповідь, задайте, наприклад, `MAX_TOKENS=4096` — додатне ціле число.

`MAX_RETRIES` керує мережевими повторами SDK; repair не входить у це значення. Timeout застосовується до мережевих операцій клієнта, тому загальний час обробки може бути більшим через повтори й repair.

Змінні, вже задані в оточенні процесу, мають пріоритет над `.env`. Обраний endpoint має підтримувати передані `temperature`, `top_p`, `response_format` із JSON Schema та `max_tokens`, якщо його задано; автоматичного підбору підтримуваних параметрів немає.

## Запуск

Довідка без звернення до моделі:

```powershell
.\.venv\Scripts\python.exe main.py --help
```

Обробка однієї статті baseline-промптом:

```powershell
.\.venv\Scripts\python.exe main.py v1 --limit 1
```

Усі 30 статей:

```powershell
.\.venv\Scripts\python.exe main.py
```

Промпт v2 і власний шлях результатів:

```powershell
.\.venv\Scripts\python.exe main.py v2 --output results/run_prompt_v2.jsonl
```

За активної `.venv` замість повного шляху до інтерпретатора можна використовувати `python`.

| Аргумент | Значення |
| --- | --- |
| `prompt_version` | `v1` або `v2`; необов'язковий, типово `v1` |
| `--limit N` | Перші N статей; N має бути додатним. Без аргументу обробляються всі TXT |
| `--output PATH` | Новий JSONL-файл; типово `results/schema-v2-enums-1/prompt_<prompt_version>_<model>_<UTC timestamp>.jsonl` |

Schema v2 використовується завжди, окремий аргумент вибору схеми відсутній. `v1` і `v2` у позиційному аргументі — лише версії промпту: `python main.py` запускає baseline-промпт v1, а `python main.py v2` — промпт v2. В обох випадках результати містять `schema_version: "v2"`.

Наприклад, `python main.py v1` із моделлю `llama3.2:3b` створює файл `prompt_v1_llama3.2_3b_<UTC timestamp>.jsonl`, а `python main.py v2` із моделлю `openai/gpt-4o-mini` — `prompt_v2_openai_gpt-4o-mini_<UTC timestamp>.jsonl`. Назва містить версію промпту, модель і час запуску. У назві моделі зберігаються латинські літери, цифри, крапки, `_` і `-`; інші послідовності символів, зокрема `/` та `:`, замінюються на `_`. Оригінальний ID моделі й версія єдиної схеми зберігаються всередині JSONL. Якщо вказано `--output`, використовується заданий шлях.

Команди обробки виконують справжні запити. Для провайдерських API вони можуть бути платними; автоматичного грошового ліміту в коді немає. Перед масовим запуском оцініть вартість: стартовий бюджет ДЗ — до $5. `--limit 1` обмежує кількість статей, але не вимикає retry або repair.

## Дані та підготовка тексту

Статті читаються з `data/sourses/hm1/texts/` у порядку `en`, `ru`, `uk`; усередині кожної папки файли сортуються за назвою. Назва каталогу **`sourses`** відповідає фактичній структурі проєкту.

Перед запитом видаляється лише розпізнаний повний початковий блок `Автори:` / `Категорії:` / `Плати:`. Заголовок, основний зміст і код зберігаються. Файли джерел не перезаписуються.

Модель отримує системний промпт і підготовлений текст однієї статті. Golden та мітки маніфесту не передаються. `document_id` береться з імені TXT й додається до журналу окремо від відповіді моделі. Golden не читається конвеєром витягування; його окремо використовує `evaluator.py` для підрахунку accuracy.

| Призначення | Файл |
| --- | --- |
| Актуальний golden Schema v2 | `data/sourses/hm1/golden.json` |
| Актуальні правила Schema v2 | `data/golden_annotation_rules_v2.md` |

## Schema v2

Модель `DevicePosting` визначена в `schema_contracts.py` і реекспортується з `main.py`. Усі поля обов'язкові, додаткові поля й `null` заборонені; типи перевіряються строго.

| Поле | Тип / значення |
| --- | --- |
| `language` | `en`, `ru` або `uk` |
| `primary_topic` | Одна з восьми тематик |
| `mentioned_platforms` | Унікальний список `arduino`, `esp32`, `esp8266`, `stm32`, `raspberry_pi`, `orange_pi` |
| `mentioned_interfaces` | Унікальний список `wifi`, `bluetooth`, `lora`, `i2c`, `spi`, `uart`, `usb` |
| `mentions_sensor` | `bool` |
| `mentions_display` | `bool` |
| `mentions_battery` | `bool` |
| `mentions_motor` | `bool` |

Допустимі тематики: `devices_automation`, `controllers_programming`, `robotics_actuators`, `sensors_measurements`, `displays_indicators`, `communications_iot`, `power_batteries`, `printing_mechanics`.

Правила відсутніх згадок — `[]` для списків і `false` для ознак. `Telegram`, `Arduino UNO`, `WiFi`, `USB` і дублікати тегів не проходять локальну валідацію; нормалізації чи автоматичного виправлення немає. JSON Schema передає enum провайдеру, а унікальність додатково перевіряє Pydantic `field_validator` без wire-обмеження `uniqueItems`. Структурна валідність не гарантує фактичної правильності; `context` сам по собі не перевіряє факти.

## Валідація та результати

Для кожної статті конвеєр перевіряє відмову, завершення відповіді й непорожній вміст, потім виконує строгу Pydantic-валідацію JSON. Після помилки JSON або схеми дозволена **одна repair-спроба** з описом помилки. Відмова, обрив, порожня відповідь або вичерпана мережевими retry помилка завершуються `failed` без окремого repair. Після невдалого repair результат також має статус `failed`.

Один рядок JSONL відповідає одній статті. Запис містить:

- ID і шлях джерела, версію схеми та модель;
- `provider`, `requested_model` (і сумісний alias `model`), `actual_model` або `null`, якщо API його не повернув;
- `contract_version` та `contract_sha256`, який враховує JSON Schema й локальні strict/unique-правила;
- версію й SHA-256 промпту, sampling та UTC-час;
- SHA-256 оригіналу, версію підготовки та SHA-256 фактичного input;
- `result.data`, статус, помилки, відповіді первинної та repair-спроб;
- `first_attempt_valid`, `repair_attempted`, `attempts`, usage і час у секундах.

`result.first_attempt_status` відрізняє `valid`, `invalid`, `refused`, `incomplete`, `empty`, `api_error`; `result.status` є фінальним статусом. Кожна відповідь також має `actual_model`. Мережеві помилки зберігають тип і HTTP-статус без текстів, які могли б містити секрети; повідомлення Pydantic і первинний вміст при repair зберігаються.

`attempts` рахує виклики клієнта разом із repair, але не внутрішні мережеві retry SDK. `first_attempt_seconds` — час першого виклику клієнта, включно з його retry; `seconds` — повна обробка всередині `extract`, разом із repair та валідацією. Читання статті й запис JSONL до цього часу не входять.

`input_tokens` та `output_tokens` сумуються за спробами; якщо usage хоча б однієї спроби невідомий, відповідний підсумок записується як JSON `null`. Вартість за цими значеннями автоматично не обчислюється.

Файл створюється без перезапису наявного й дописується після кожної статті. Після `failed` конвеєр переходить до наступної. Якщо процес перервати, уже записані рядки залишаються; автоматичного resume немає. Надруковане `Валідних: X/Y` означає проходження схеми після можливої repair-спроби, а не точність на golden.

## Оцінювання на golden

Оцінити новий контракт без викликів моделей (після появи нових прогонів):

```powershell
.\.venv\Scripts\python.exe evaluator.py --contract schema-v2-enums-1
```

Оцінити окремий прогін і задати новий файл звіту:

```powershell
.\.venv\Scripts\python.exe evaluator.py results/prompt_v1_gpt-4o-mini_20261026T091241044332Z.jsonl --output results/evaluation/gpt_v1.json
```

Можна передати кілька JSONL через пробіл; `--golden PATH` задає інший еталон Schema v2. Типовий golden — `data/sourses/hm1/golden.json`. Типовий вихід — новий `results/evaluation/<contract>/golden_<UTC timestamp>.json`; наявні файли не перезаписуються. JSON містить контракт, його хеш, конфігурацію кожного прогону, хеші golden і JSONL, метрики та розбіжності.

Без шляхів evaluator шукає `results/*.jsonl` та `results/schema-v2-enums-1/*.jsonl`. Для історії задайте `--contract schema-v2-strings-1`. Без цього аргументу дозволений лише один контракт у знайдених файлах; змішані та невідомі контракти відхиляються. Явно переданий файл іншого контракту спричиняє помилку, а не мовчазне відфільтровування.

### Правила порівняння

- Оцінюється фінальний `result.data` після можливої repair-спроби. `ok` має бути `true`, статус — `success`, дані мають проходити валідацію свого контракту: строгого нового або замороженого legacy.
- `language`, `primary_topic` та чотири `mentions_*` порівнюються точно.
- Для `mentioned_platforms` і `mentioned_interfaces` застосовується **exact-set match**: порядок не впливає на збіг, зайвий або пропущений тег дає нуль за поле. У новому контракті дублікати роблять всю відповідь невалідною. Лише legacy допускає їх і записує в `duplicate_list_values` без впливу на exact-set.
- Нормалізації немає: `Wi-Fi`, `wifi` та ` wifi ` — різні значення. `[]` збігається лише з `[]`.
- Знаменник accuracy — весь golden. Відсутній документ, `failed` або невалідна відповідь отримує нуль за всі вісім полів, навіть якщо окремі значення могли бути правильними. Часткові чи `null`-об'єкти не доповнюються автоматично.
- `field_accuracy` — правильні значення відповідного поля / кількість golden-документів. `aggregate_accuracy` — середнє арифметичне восьми field accuracy з однаковими вагами.
- `content_accuracy` — середнє семи field accuracy без `language`; `content_field_accuracy` показує ці поля окремо. Знаменники враховують missing/failed/invalid.
- Додаткові `list_metrics` рахують **micro** TP/FP/FN, precision/recall/F1 за унікальними тегами всіх golden-документів. Для missing/failed/invalid передбачення вважається порожнім: очікувані теги дають FN. Невизначені частки записуються як JSON `null`; коли всі списки порожні, exact-set accuracy залишається визначеною, а P/R/F1 — `null`.
- Не-golden документи не входять у метрики; їх кількість записується окремо. Дублікати ID, змішані конфігурації або невідповідність source-хешів зупиняють оцінювання. Прогони з різним `input_sha256` для того самого golden ID потрібно оцінювати окремими командами.
- Якщо хоча б один golden-запис не має статусу `approved`, весь звіт позначається `provisional: true`. Evaluator не змінює статусів розмітки.
- Для нового контракту додатково звіряються ім'я TXT з ID, реальні байти джерела, версія підготовки й SHA-256 підготовленого тексту.

Приклад: golden `["wifi", "bluetooth"]` та відповідь `["bluetooth", "wifi"]` дають exact-set accuracy 1. Відповідь `["wifi", "usb"]` дає accuracy 0, але TP=1, FP=1, FN=1. P/R/F1 звітуються окремо й не додаються до aggregate accuracy.

Evaluator не обчислює latency p50/p95, вартість або первинну валідність; це окремі метрики прогонів. Він також не доводить, що всі значення golden фактично правильні.

## Агреговані метрики прогонів

Цей агрегатор працює за всіма записаними статтями, а не лише за golden. Він не викликає моделі:

```powershell
.\.venv\Scripts\python.exe aggregate_runs.py --contract schema-v2-enums-1
```

Правила вибору файлів і `--contract` такі самі, як в evaluator. Створюються нові файли `results/metrics/<contract>/runs_<UTC timestamp>.json` і `.md`. Уже сформована [історична таблиця восьми конфігурацій](results/metrics/runs_20261026T101448227707Z.md) має відповідний [JSON](results/metrics/runs_20261026T101448227707Z.json); вона описує strings-контракт.

Для окремих прогонів задайте їхні шляхи через пробіл. `--output` задає новий JSON-файл; поряд створюється однойменний Markdown. Наявність будь-якого з двох файлів зупиняє запис:

```powershell
.\.venv\Scripts\python.exe aggregate_runs.py results/prompt_v1_gpt-4o-mini_20261026T091241044332Z.jsonl --output results/metrics/gpt_v1.json
```

`aggregate_runs.py` відповідає за файли та таблиці; розрахунки винесено в `run_metrics.py`. Групування враховує модель, версію й хеш промпту, sampling, версію схеми та підготовки. Еквівалентні числові параметри `0` і `0.0` належать до однієї групи. Повторення ID усередині файлу або повторне передавання того самого файлу — помилка; різні файли тієї самої конфігурації підсумовуються як повторні спостереження. Звіт показує кількість файлів, обробок і унікальних ID. Конфлікти source/input-хешів для одного ID відхиляються.

### Методика агрегації

- Знаменник валідності — всі записані обробки групи, включно з failed. До repair використовується `first_attempt_valid`; після repair — `ok` зі статусом `success`, повторно перевірений за схемою. Окремо зберігаються кількість і частка repair та успішність repair.
- Latency рахується двічі: для `first_attempt_seconds` і для `seconds`. Невдалі обробки також включаються. Перцентилі — **nearest rank**: елемент `ceil(p*N)` відсортованого часу. Для N=30 p50 — 15-те, p95 — 29-те значення. Одиниці — секунди.
- Якщо час частини обробок відсутній, перцентилі обчислюються лише за відомими значеннями й позначаються `complete=false`, а в таблиці — зірочкою. Кількість пропусків збережено; за повної відсутності часу значення — `null`.
- Usage включає repair, якщо він врахований первинним журналом. Для неповного usage повний підсумок токенів і API-вартість — `null`, відома частина зберігається окремо. Невід'ємні цілі токени, скінченний невід'ємний час і несуперечливі прапорці перевіряються; пошкоджені дані зупиняють агрегацію.
- Для `gpt-4o-mini` в `MODEL_PRICING` зафіксовано тариф від 26.10.2026: input $0.15/1M, output $0.60/1M, із посиланням на джерело. Розрахунок використовує повну ціну input без кеш-знижки; це оцінка, не рахунок OpenAI. Тариф автоматично не оновлюється.
- Для нового `provider=ollama` нульові лише зовнішні API-витрати, без обладнання й електроенергії. Для невідомого тарифу чи невідповідності провайдера тарифному snapshot вартість — `null`. Лише в історичних JSONL provider відсутній: відповідність gpt-4o-mini тарифу OpenAI та llama3.2:3b локальному запуску є припущенням.
- API USD/1000 = оцінена вартість групи / кількість записаних обробок × 1000. Це екстраполяція для таких самих текстів, відповідей і частоти помилок; вона не гарантує бюджет довільних 1000 статей.
- Читання TXT та запис результатів не включені в latency. Retry входить у час виклику; repair і валідація — у повний час. Cold start окремо не позначений і може бути включений; steady-state latency та кількість прихованих мережевих retry з цих даних не відновлюються.

Повністю відсутні в JSONL запити невідомі агрегатору: він описує збережені обробки, а не перевіряє виконання плану запуску. У JSON і Markdown записуються припущення, тарифні джерела, повна конфігурація та SHA-256 кожного використаного JSONL.

## Генерація чернетки REPORT

`generate_report.py` офлайн поєднує явно вибрані JSON-звіти evaluator та агрегатора. Приклад створення нової чернетки з поточних звітів:

```powershell
.\.venv\Scripts\python.exe generate_report.py --evaluation results/evaluation/golden_20261026T095934403348Z.json --metrics results/metrics/runs_20261026T101448227707Z.json --output REPORT.review.md
```

Без `--output` використовується `REPORT.<contract>.draft.md`. Історичний [REPORT.md](REPORT.md) залишається незмінним; новий фінальний звіт створюється після нових реальних експериментів. Якщо вибраний файл існує, генератор зупиняється без перезапису. `--examples 3`, `4` або `5` задає кількість прикладів; типово 5. Якщо різних статей із розбіжностями менше, виводиться доступна кількість із поясненням.

Генератор перевіряє хеш golden та кожного первинного JSONL і повторно обчислює оцінки й метрики для звірки. Два звіти мають охоплювати той самий набір первинних файлів. Зіставлення враховує всю конфігурацію, зокрема хеш промпту й версію підготовки. Неузгоджені, змінені або застарілі звіти потрібно сформувати повторно через `evaluator.py` і `aggregate_runs.py`. Тарифи перевіряються за поточним `MODEL_PRICING`, тому після зміни тарифної таблиці потрібна нова агрегація.

Чернетка містить загальну таблицю порівняння, accuracy восьми полів, micro precision/recall/F1 списків, latency й usage, тарифні припущення та посилання на джерела з хешами. Повторні прогони однієї конфігурації враховуються за всіма спостереженнями. Для прикладів добираються різні типи розбіжностей і, по можливості, різні статті; показуються ID, конфігурація, очікуване/фактичне значення та джерела. Якщо текст статті доступний, його хеш також перевіряється.

**До завершеного звіту автор має:** прочитати приклади й пояснити причини, сформулювати висновки, обрати production-конфігурацію та умови перегляду рішення. Ці місця позначені `[ЗАПОВНЮЄ АВТОР]`. Provisional-оцінки лишаються позначеними; програма не затверджує golden чи production-рішення й не створює `REPORT.md` замість автора. Перевірену та доповнену чернетку можна використати як основу `REPORT.md`.

## Тести

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тести використовують підставний клієнт і HTTP `MockTransport`, без зовнішньої мережі й платних викликів. Перевіряються валідація, repair, відмови, usage, конфігурація, необов'язковий ліміт токенів, підготовка тексту, хеші, обмеження вибірки та запис JSONL. Вони не підтверджують якість або сумісність реальних моделей.

## Типові проблеми

| Симптом | Що перевірити |
| --- | --- |
| `ModuleNotFoundError: openai` | Установіть `requirements.txt` саме в інтерпретатор, яким запускаєте скрипт |
| `Не задано API-ключ` | Перевірте змінну `LLM_PROVIDER` і ключ відповідного провайдера в `.env` або оточенні процесу |
| `FileExistsError` | Виберіть новий `--output` або приберіть цей аргумент для нового імені за часом |
| Помилка `response_format` або sampling | Перевірте підтримку JSON Schema й усіх переданих параметрів обраною моделлю/endpoint |
| Помилка з'єднання з Ollama | Перевірте сервер, `OLLAMA_BASE_URL` та наявність моделі з указаним ID |
